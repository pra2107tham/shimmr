Shimmr

Zero to paid,
as one person lives it.

Nine moments between a stranger landing on the site and a team paying for a bridge. What they see, what they feel, and exactly what we're offering at each point — including the one stretch where we lose them.

The shape of it

Attention peaks in the first ten minutes, then collapses

This curve is the whole product problem. A free tool that runs silently is a tool people stop thinking about — and you cannot sell to someone who forgot you exist.

Stage by stage

The nine moments

01

The site

First 30 seconds · they are skeptical

They arrived from a comment thread. They have closed four AI dev-tool sites this month, all of which wanted a demo booking. They are scanning for a reason to close this one too.

Sees

One sentence saying what it does. A 20-second recording of a real repo being indexed and a real question answered. The install command, in copyable text, above the fold. Pricing, without clicking. The words “no account needed”.

Feels

“Oh — they're just showing me the thing.”

We offer

  • The claim and the proof on the same screen
  • A command they can run before trusting us
  • Honest pricing with the free half stated first
Kills itA gradient hero, a “Book a demo” button, or an email field before the download. This audience reads those as “the product isn't ready.”
02

Install

60 seconds · quietly suspicious
$ curl -fsSL shimmr.dev/install | sh Installed shimmr 0.1.0 → /usr/local/bin/shimmr $ shimmr init I'd like to change 2 files. Here's exactly what: ~/.claude.json + 4 lines (adds shimmr as an MCP server) ~/.cursor/mcp.json + 4 lines (same) Nothing else is touched. Show the diff with --dry-run. Continue? [Y/n]

Sees

One binary, no runtime to install first. A prompt that names every file it wants to edit, before editing it.

Feels

“It asked. Nothing else asks.”

We offer

  • Single static binary — no Node, no Python, no Docker
  • Auto-detects the agents they already use
  • --dry-run, and consent before touching config
Kills itSilently rewriting ~/.claude.json. For an audience that chose us over a cloud tool on privacy grounds, an unannounced write to their home directory is the whole pitch contradicting itself in the first minute.
03

First index

60 seconds · peak anxiety, then relief

This is the moment they point a tool they downloaded four minutes ago at their company's private source code. Everything we say about trust is cashed out here or nowhere.

$ shimmr index . Reading ████████████████████ 1,247 files Linking ████████████████████ 8,932 functions Done in 41s. 14,201 connections mapped. Stored at ~/.shimmr/graph Network 0 bytes sent, 0 connections opened Don't take my word for it: shimmr verify --network

Sees

Speed. Then a network line that reports zero — and a command to check that claim themselves rather than trust it.

Feels

“It let me verify instead of asking me to believe.”

We offer

  • A whole repo mapped in under a minute
  • Egress reported as an observable number, every run
  • shimmr verify --network — the trust claim as a test they can run
Kills itA silent progress bar. Every second without output on a private repo is a second they spend wondering what is being uploaded.
04

The first real answer

2 minutes · the “oh” moment

They ask the question they always end up answering for new hires: where do we check whether a user can delete a project?

Instead of grepping and opening 30 files, the agent: → searched the map for permission-shaped symbols → traced who calls them, two hops out → read the four functions that actually mattered Answer in ~2s: api/permissions.go:142 called from 4 places, all listed

Sees

Their own agent, in their own editor, answering a structural question with exact locations instead of a paragraph of hedging.

Feels

“It actually knows the codebase.”

We offer

  • The map, and the agent instructions that make it get used
  • Answers with file and line, not guesses
  • Roughly an order of magnitude fewer tokens per question
Kills itThe agent ignoring our tools and grepping anyway. Everything upstream of this moment is wasted if the model doesn't reach for the map — so tool descriptions and the agent-side instructions are product surface, not configuration.
05

Weeks one to three

Invisible · and that is the danger

It just works. Branch switches reindex on their own. Nothing breaks, nothing asks for attention. Their agent is quietly better and they have stopped attributing that to us.

Sees

Nothing. No prompts, no popups, no update nags.

Feels

Nothing at all — which is correct for infrastructure, and fatal for a business.

We offer

  • Silence, reliability, automatic reindex on branch change
  • No account, no email, no telemetry
The real problemWe chose a free tier with no signup, so at this point we have no email, no account, and no way to reach them. If they never run a Shimmr command again, we have permanently lost a user who is actively benefiting from us. Stage 6 exists entirely to solve this.
06

The weekly summary

Day 7 · the one touchpoint we get

Not a vanity dashboard. This is the only moment in the free tier where the product reminds someone it exists — so it has to be worth opening, and it has to arrive without us having their email.

$ shimmr stats This week 342 questions answered from the map search_graph 118 ████████████████ get_code_snippet 87 ████████████ trace_path 64 █████████ get_architecture 41 █████ Tokens saved ~2.1M (the method: shimmr stats --method) Left your laptop 0 bytes

Sees

A number big enough to screenshot, and a flag that shows exactly how it was calculated.

Feels

“Huh. I should show someone this.”

We offer

  • Usage they can see, locally, with no account
  • A savings figure that shows its own working
  • A shareable artifact — the top of the referral loop
Kills itA tokens-saved number we can't defend. The first CTO who asks “how did you calculate that?” and gets a shrug stops believing the zero-bytes line too.
07

A teammate notices

Week 3–4 · growth, for free

Someone pairs with them and asks how their agent found that so fast. The honest answer is one command long, which is the entire distribution strategy.

Sees

Their teammate installing it in under two minutes, on the strength of a recommendation rather than a sales page.

Feels

Mildly proud. They found it first.

We offer

  • An install short enough to say out loud
  • Zero friction for the second user — still no account
  • The stats output as something worth pasting into Slack
Kills itNothing, at this stage. This is the one moment where asking for nothing is strictly the right move — a signup wall here converts a recommendation into a shrug.
08

Making it the team's

Month 2 · the first thing we ask for

Four engineers now run it, each with their own settings and their own ignore rules. Someone wants everyone on the same configuration. This is the first time an account is genuinely the answer rather than a toll booth.

$ shimmr team create acme Created. Share this with your team: shimmr team join acme-7f3a2b They'll pick up your shared config and ignore rules. Free — we ask for an email so we can tell you when something breaks, and for nothing else.

Sees

An account that solves a problem they actually have, offered at the moment they have it — not at download.

Feels

“Fine, that's a fair trade.”

We offer

  • Free org, shared config and ignore rules, one-line join
  • A licence identity everything paid later hangs off
  • The email we've gone eight stages without asking for
Kills itAsking any earlier. The account is only defensible here because it is doing real work; at stage 2 the same request is a signup wall in a costume.
09

Connecting GitHub

Month 2–3 · the first money

The trigger is a specific irritation: the agent confidently suggests a refactor the team already tried and reverted in March. It knows what the code is; it has no idea what the team has already learned.

$ shimmr connect github Connecting acme/api … Issues 1,204 indexed Pull requests 3,891 indexed Stored locally, alongside your code map. 14 days free, then $X/seat/month. Ask your agent why something is the way it is.

Sees

The agent answering “why is this retry loop here?” with the incident and the PR that put it there.

Feels

“It knows things I never told it.”

We offer

  • Issues and PRs as agent context, indexed on their machine
  • The reasoning behind the code, not just its shape
  • Later: OpenHands and other runtimes, scheduled automations
Kills itSending repo history to our servers to do the indexing. The entire reason they trust us is the boundary — a paid feature that quietly crosses it costs more than it earns.
Rules that hold at every stage

What we never do

These are cheap to keep and extremely expensive to walk back. Each one is a promise a competitor with a cloud backend structurally cannot make.

Never gate the download behind an email

Stages 1 through 7 ask for nothing. The account arrives at stage 8, when it earns its place.

Never touch a config file without saying so

Every write is named before it happens and reversible after. --dry-run is a first-class flag, not a debugging aid.

Never claim local-only without a test

The zero-bytes line is printed from a real measurement, and shimmr verify --network lets the customer reproduce it.

Never publish a number we can't derive

Tokens saved ships with --method. A figure we can't defend contaminates the claims that are true.

Never wall a local capability

Nothing that runs on their machine is ever withheld to force an upgrade. The paywall sits at the boundary, nowhere else.

Never send usage anywhere by default

Sharing is opt-in, off by default, and prints the exact payload before the first send.

Before we build

Three things this journey decides for us

Each one changes what gets built in Phase 1, so they are worth settling now rather than discovering at stage 5.

How does the day-7 summary reach someone who never runs a command?
Stage 5 is the gap, and shimmr stats only helps people who remember to type it. Options: print a one-line weekly summary on the next agent session, an optional email at stage 2 purely for this, or accept the loss and lean on stage 7 word-of-mouth. Leaning: a single quiet line in the terminal on first use each week — no email, no popup, consistent with every rule above.
Do we ship agent-side instructions, or only tools?
Stage 4 dies if the model doesn't reach for the map. Shipping a short instruction file into the agent's config makes adoption dramatically more reliable — and means writing to one more file at stage 2. Leaning: ship them, name the file in the consent prompt, keep them short enough to read.
What is the boundary rule for connected features?
Stage 9 pulls GitHub data down. If that indexing happens on our servers, the promise breaks. Leaning: the customer's machine calls GitHub directly with their own token, and we never see the payload — which is harder to build and is the entire reason anyone would pay us rather than a competitor.
